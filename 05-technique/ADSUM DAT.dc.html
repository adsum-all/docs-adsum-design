03 - ARBORESCENCE DU REPOSITORY

Multi-dépôts organisés en groupe & sous-groupes

Un groupe racine contient des sous-groupes (organisation logique, pas de code), qui contiennent les dépôts (repositories Git où vit le code). Les applications sont séparées du back-office ; les services Python sont isolés ; la base partagée est pilotée par un seul dépôt de migrations (source unique du schéma). Cela permet à plusieurs équipes de travailler sans collision et de déployer chaque socle indépendamment.

Application & back-office séparés

Deux dépôts distincts (adsum-mobile côté membre/terrain, adsum-back-office côté admin) : deux cycles de déploiement, deux surfaces d'attaque. Ils partagent la même base et les mêmes paquets. La priorité est l'application Android (React + Capacitor), déclinée ensuite en iOS, web mobile et web desktop depuis le même socle.

Une seule source de vérité pour la base

Le schéma vit dans un seul dépôt (deployment/database) : migrations versionnées + seed. Aucun autre dépôt ne modifie la structure. PostgreSQL est 100 % autonome et auto-porteur : hébergé sur Supabase aujourd'hui, migrable vers n'importe quel PostgreSQL standard sans réécriture (pas de dépendance propriétaire).

04 - MODÈLE DE DONNÉES (DDL)

Schéma PostgreSQL - modèle complet

Le modèle compte 17 tables réparties en quatre domaines : identité & appartenance (membre, commission, appartenance M-N, engagement, document), activité & présence (événement, présence, jeton QR, terminal, comptage volet B), compte & traçabilité (utilisateur, session, audit, notification) et paramétrage & campagnes (parametre, import_lot, recensement, recensement_reponse). Conventions communes : clé primaire uuid (gen_random_uuid()), dates en timestamptz, suppression logique uniquement, et cree_le systématique. Les pièces d'identité ne sont jamais une table (voir RGPD plus bas).

CREATE TABLE membre (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  matricule     text UNIQUE NOT NULL,   -- ADS-000123
  email         text UNIQUE NOT NULL,
  nom           text, prenoms text, telephone text, adresse text,
  commission_id uuid REFERENCES commission(id),
  groupe        text, photo_url text,
  statut        text DEFAULT 'actif',   -- actif|inactif
  verifie       boolean DEFAULT false,
  cree_le       timestamptz DEFAULT now(),
  desactive_le  timestamptz            -- suppression logique
);

CREATE TABLE presence (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  membre_id    uuid REFERENCES membre(id),
  evenement_id uuid REFERENCES evenement(id),
  mode         text,   -- salle | en_ligne
  arrivee      timestamptz, depart timestamptz,
  methode      text,   -- scan | manuel | lien
  terminal_id  uuid REFERENCES terminal(id),
  UNIQUE (membre_id, evenement_id)   -- 1 membre = 1 présence
);

CREATE TABLE jeton_qr (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  membre_id   uuid REFERENCES membre(id),
  payload     bytea,   -- signé Ed25519
  version_cle int,
  revoque     boolean DEFAULT false, revoque_le timestamptz
);

CREATE TABLE recensement (      -- campagne annuelle (§ présentation)

05 - PIPELINE DE DONNÉES

Du scan à la statistique

1
Capture. Le terminal lit le QR, vérifie la signature en local (packages/qr), écrit la présence dans une file persistante (IndexedDB/SQLite) - fonctionne 100 % hors-ligne.
2
Synchronisation. Au retour réseau, lot envoyé à POST /presences/sync. Clé d'idempotence (membre_id, evenement_id) → un rejeu n'insère jamais de doublon (UPSERT).
3
Persistance & événement. FastAPI valide (Pydantic), écrit en PostgreSQL, publie un message Redis pub/sub.
4
Temps réel. Le WebSocket /ws/evenements/{id} pousse la mise à jour ; les dashboards se rafraîchissent en quelques secondes.
5
Agrégation & restitution. Vues SQL matérialisées (taux, par commission, salle/en ligne dédoublonné) ; exports CSV/Excel et rapports PDF générés par worker.

Zoom - synchronisation idempotente (zéro perte, zéro doublon)

Passerelles vers les services externes (anti-corruption)

Principe non négociable : aucune dépendance directe à un fournisseur externe. Tout service hors du système (e-mail, SMS, notifications push, paiement, géo-IP, stockage objet) est appelé uniquement au travers du dépôt adsum-gateway, via une interface interne stable (un « port »). Chaque fournisseur a son adaptateur dédié derrière ce port. Le code métier ne connaît jamais le fournisseur : il parle au port. Conséquence : on change de fournisseur sans toucher au métier, et une panne d'un fournisseur reste isolée (jamais de blocage global).

07 - SÉCURITÉ & CRYPTOGRAPHIE

Mécanismes de protection

QR signé Ed25519

  • Clé privée sur serveur uniquement (jamais distribuée)
  • Clé publique en cache sur les terminaux
  • Vérification hors-ligne < 1 s, jeton révocable
  • Rotation de clé versionnée (version_cle)

Accès & secrets

  • JWT court + refresh ; 2FA par code e-mail
  • Mots de passe : hachage Argon2
  • RBAC appliqué à chaque route (moindre privilège)
  • Secrets via variables d'env / coffre, jamais en dépôt

Données

  • TLS en transit · chiffrement au repos (pièces)
  • Minimisation RGPD : pièces supprimées après validation
  • Conservation paramétrable · export/suppression sur demande

Durcissement

  • Rate-limiting + verrouillage anti-force-brute
  • CORS strict, en-têtes de sécurité (CSP, HSTS)
  • Validation stricte des entrées (Pydantic)
  • Journal d'audit immuable de toute action sensible

11 - TRAÇABILITÉ & CONFORMITÉ

Tout est démontrable

En cas d'audit ou de commission d'enquête, la chaîne de preuve est complète :
  • Journal d'audit immuable : acteur, action, objet, horodatage, IP - pour chaque opération sensible.
  • Versionnage des engagements : preuve horodatée de signature (consentement, confidentialité, lettre).
  • Suivi documentaire : statut demandé → reçu → lu → traité, daté des deux côtés.
  • Tracking connexions : géolocalisation, heures, appareil.
  • Migrations Alembic : historique complet des évolutions du schéma.
  • Git : historique de tout changement de code, lié à la CI.
Aucune action n'est anonyme ou non datée ; aucune donnée n'est modifiée sans trace.
12 - DÉCISIONS D'ARCHITECTURE (ADR)

Choix structurants & justifications

ADR-01 · ACTÉPointage hors-ligne par conception
Réseau non garanti en événement. Décision : vérification QR locale + file persistante + sync idempotente. Conséquence : clé publique embarquée, logique QR dupliquée côté client (TS).
ADR-02 · ACTÉDeux langages : TypeScript + Python
TS unifie les clients (Capacitor) ; Python/FastAPI accélère le back et offre un écosystème crypto/données mûr. Contrats REST typés au milieu.
ADR-03 · ACTÉEd25519 plutôt que QR opaque
Signature asymétrique → vérifiable hors-ligne sans appel serveur, infalsifiable, révocable. Alternative (QR en base interrogé) rejetée car dépend du réseau.
ADR-04 · ACTÉMinimisation des pièces d'identité
Pièces chiffrées temporaires sur S3, supprimées à la validation. RGPD allégé, pas d'AIPD lourde. Seule la preuve de validation reste.
ADR-05 · ACTÉCodes par e-mail (pas de SMS au départ)
E-mail + push couvrent gratuitement 2FA/MDP temporaire/signatures. SMS branchable plus tard si budget - l'architecture le prévoit en option.
